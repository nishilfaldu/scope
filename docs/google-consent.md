# Google connections and consent

Scope requests service authority only. Gmail, Calendar, and combined Files remain separate connections, with the same three callback paths. Google OAuth does not authenticate a Scope user.

| Connection                    | Requested scope (under `https://www.googleapis.com/auth/`) | Identity lookup                                                 | Stored service key / display                                      |
| ----------------------------- | ---------------------------------------------------------- | --------------------------------------------------------------- | ----------------------------------------------------------------- |
| Gmail                         | `gmail.modify`                                             | `GET /gmail/v1/users/me/profile?fields=emailAddress`            | `gmail:<lowercase emailAddress>` / returned mailbox email         |
| Calendar                      | `calendar`                                                 | `GET /calendar/v3/calendars/primary?fields=id`                  | `calendar:<id>` / primary calendar ID                             |
| Files (Drive + Docs + Sheets) | `drive`                                                    | `GET /drive/v3/about?fields=user(permissionId,emailAddress,me)` | `drive:<permissionId>` / email, or `Drive account <permissionId>` |

[Gmail getProfile](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users/getProfile) permits `gmail.modify` and returns the mailbox email, not an immutable Google subject. A mailbox rename produces a new connection on reconnect; remove the obsolete connection and select the new one in slices. Scope does not merge accounts by aliases, dots, or plus addressing, or claim lifetime identity across email reassignment.

[Calendar get](https://developers.google.com/workspace/calendar/api/v3/reference/calendars/get) resolves `primary` to the authenticated user's calendar. Its ID identifies that service resource; it is not asserted to be the current account email or an OpenID subject. The [Calendar resource](https://developers.google.com/workspace/calendar/api/v3/reference/calendars) defines `dataOwner` only for secondary calendars, so it cannot identify the primary account. Scope ignores it and never substitutes a calendar title as identity.

[Drive about.get](https://developers.google.com/workspace/drive/api/reference/rest/v3/about/get) returns the requesting user's information under existing Drive authority. Scope requires `user.me === true` and a nonempty `permissionId`. The [User schema](https://developers.google.com/workspace/drive/api/reference/rest/v3/User) allows email to be absent in some contexts; absence does not prevent connecting, and email changes do not change the Files key. No profile name/photo is requested.

The full Drive scope already authorizes the broker's Docs [get](https://developers.google.com/workspace/docs/api/reference/rest/v1/documents/get), [create](https://developers.google.com/workspace/docs/api/reference/rest/v1/documents/create), and [batchUpdate](https://developers.google.com/workspace/docs/api/reference/rest/v1/documents/batchUpdate), and Sheets [get](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/get), [create](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/create), [values.get](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/get), and [values.update](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/update). Separate `documents` and `spreadsheets` consent is redundant. `drive.file` is not equivalent: the existing broker lists and reads existing files without a Picker selection flow. Resource operations and scraping logic are unchanged.

## Grant validation

`convex/domain/apps.ts` is the shared check for code exchange, completion, stored grants, refreshed tokens, credential issuance, and broker operations. Accepted scope sets are exactly `{gmail.modify}`, `{calendar}`, and `{drive}` (full Google scope URLs). Duplicates do not change a set. There are no identity-scope or old Files-scope exceptions, and no aliases are accepted without evidence that Google requires them for these requests.

Evidence: the prior live `openid` addition occurred when Scope requested `userinfo.email`. All later service-only browser attempts stopped at Google's unverified-app warning before token exchange. We have not observed a service-only token carrying any extra scope. The prior identity and redundant Files allowlists were unsupported allowances and have been removed.

[Google's incremental authorization documentation](https://developers.google.com/identity/protocols/oauth2/web-server#incrementalAuth) describes project-wide combined grants when including prior scopes; Scope explicitly sends `include_granted_scopes=false`. It does not establish that these service-only requests will contain old project-wide scopes. [Google also documents scope-name mapping](https://developers.google.com/identity/protocols/oauth2#3.-examine-scopes-of-access-granted-by-the-user.): that general behavior is not evidence that any of these seven removed exceptions is necessary. Extra scopes with this configuration remain an unverified possibility, not an observed requirement.

Requested scope is the consent boundary, but it cannot constrain a broader bearer token after delivery. `convex/http/mint.ts` returns Google access tokens directly for Gmail and Calendar; actual token authority therefore matters. Files keeps its token server-side and its fixed operation allowlist in `convex/http/googleBroker.ts` provides a separate capability boundary. Exact upstream scope rejection is conservative for Files, but is kept consistent with the service-only contract; no evidence justifies widening it. If live service-only grants prove inseparable from additional authority, investigate provider token isolation or a fully brokered design before adding exceptions. Do not strip scope metadata or accept old grants to disguise a mismatch.

Scope stores the actual reported scopes instead of deleting extras to make validation pass. Omitted scope on refresh inherits the verified stored grant; an explicit empty, malformed, partial, or extra scope never inherits it. `convex/oauth/access.ts` persists a successful refresh before checking the scope boundary to preserve rotated refresh credentials; a mismatched grant is recorded and fails subsequent attempts too. No rejected token is delivered to an agent or resource API. Google authorization continues to use `include_granted_scopes=false`.

## Storage, reconnect, and disconnect

`saveConnection` deduplicates by `(userId, app, providerUserId)` and increments both grant version and connection generation on reconnect. `refreshConnection` fences writes by that key, grant version, and refresh lease. Slice bindings and broker credentials reference connection IDs; reconnect invalidates older broker credentials. `statusesForApps` and request/account displays use `login`, not a Google cross-app subject, for presentation. Scope ownership always comes from its authenticated user ID.

This is a clean break from the previous userinfo-sub keys. No schema migration, backfill, or dual-key lookup is provided. Remove old Google connections and reconnect before relying on new keys; otherwise old and new rows can coexist for the same physical account. No data is cleared automatically by deployment.

[Google revocation](https://developers.google.com/identity/protocols/oauth2/web-server#tokenrevoke) invalidates all grants for the project, across its OAuth clients. Comparing service-local IDs cannot prove that another app or Scope user is unaffected. Google disconnect therefore deletes only the selected local connection, blocking future mints and broker operations. It never calls Google's revoke endpoint. To revoke the full upstream grant, remove Scope in Google Account settings; all Google apps then need reconnection. Previously issued Gmail/Calendar bearer tokens can remain valid until expiry. Other providers retain best-effort upstream revocation.

Concrete cost: each connection still makes one token exchange plus one identity request, with partial fields; there is no extra lookup on mint/refresh, no identity table/index, and no new production dependency. Vite 8.2.2, already used transitively by Vitest, is declared directly for Convex test typechecking. Disconnect removes up to three indexed cross-app lookups and the Google revoke request. Removing userinfo and redundant scope requests avoids three unnecessary permission declarations for Files (email, Docs, Sheets).

## Google Console

In Google Auth Platform → Data Access, retain only these Scope service scope declarations:

- `https://www.googleapis.com/auth/gmail.modify`
- `https://www.googleapis.com/auth/calendar`
- `https://www.googleapis.com/auth/drive`

Remove `https://www.googleapis.com/auth/userinfo.email`, `https://www.googleapis.com/auth/userinfo.profile`, `openid`, `https://www.googleapis.com/auth/documents`, and `https://www.googleapis.com/auth/spreadsheets` if declared for Scope. No identity scope needs adding. Keep Gmail, Calendar, Drive, Docs, and Sheets APIs enabled: removing a redundant scope does not remove an API dependency. Keep the existing `/api/gmail/callback`, `/api/calendar/callback`, and `/api/files/callback` redirects on `https://bright-dinosaur-692.convex.site`. No Console changes were made by the implementation.

Changing declarations does not erase existing Google grants. Consent checkboxes and the “already has access” summary are not proof of effective token scopes; Scope validates token responses. A fresh-consent test requires removing the prior Scope grant in Google Account and reconnecting. Do not bypass an unverified-app warning during automated testing.

## Comparable provider paths (inspection only)

Google alone used an exact returned scope-set check. `convex/oauth/providers/vercel.ts` explicitly requests `openid email profile offline_access`, then calls Vercel userinfo for `sub`; it does not reject extra returned scope strings. `airtable.ts` requests `user.email:read`, calls `/v0/meta/whoami` for `id`, and can display a fallback without email. `zoom.ts` calls `/v2/users/me` for `id` and depends on Console-configured scopes. `slack.ts` uses its OAuth response's user ID plus `users.info`; `linear.ts` uses GraphQL viewer ID; `github.ts` uses `/user`; `notion.ts` uses workspace/bot IDs from the exchange. None has Google's exact-set failure path. A failed/missing identity can still fail connection through `grantFromTokenPayload` / `tables/oauthStates/finish.ts`; removing provider-specific identity permissions without checking those APIs would be a different task. Other providers are unchanged.
